# Architecture

## Layers

| Path | Responsibility |
|---|---|
| `src/cli/main.ts` | Entry point. Loads `.env` files and registers the commands |
| `src/cli/command.ts` | Shared options, env var fallbacks, JSON or text output choice |
| `src/commands/*.ts` | One file per command: argument schema, handler, output |
| `src/core/configurator.ts` | `SaleorConfigurator`, the facade commands call for introspect, diff and deploy |
| `src/core/service-container.ts` | `ServiceComposer` builds every repository and service around one GraphQL client |
| `src/core/diff` | `DiffService`, one comparator per section, output formatters |
| `src/core/deployment` | Deployment stages, the pipeline that runs them, reports |
| `src/core/validation/preflight.ts` | Duplicate identifier and default customer type checks before deploy |
| `src/modules/<entity>` | Per-entity repository (GraphQL operations) and service (create, update, lookup) |
| `src/modules/config` | Reading the store into a config (`ConfigurationService`), YAML read and write, the Zod schema |
| `src/lib/graphql` | urql client with auth, retry and the request governor |
| `src/lib/errors` | `BaseError` and its GraphQL and Zod subclasses |
| `src/index.ts`, `src/engine.ts` | Library entry points, see [library.md](library.md) |

## introspect

`ConfigurationService` reads every section from Saleor, maps it to the config shape and writes YAML. When `config.yml` already exists, `DiffService` first compares the file with the store so the command can show what will change.

## diff

`DiffService.compare` loads the local file and the remote config, then runs the comparator for each selected section. Each comparator is a spec for `entityComparator`, which matches entries by identifier ([ENTITY_REFERENCE.md](ENTITY_REFERENCE.md)) and returns one `CREATE`, `UPDATE` or `DELETE` result per object deploy writes; a category tree yields one result per category. Each change carries the path from its entity to the changed value. Formatters render changes through `render-change.ts` and turn the summary into a table, JSON or a GitHub comment.

## deploy

1. Load and validate `config.yml`, then run the preflight checks.
2. Compute the diff summary; stop here for `--plan`, or when `--fail-on-delete` finds deletions.
3. Run the stages from `src/core/deployment/stages.ts` in order. Each stage skips itself when the summary has no changes for its section. A failed stage is recorded and later stages still run.
4. Print the summary, save the report, and exit with the code for the overall status.

Stages create and update entities. Updates can remove items nested in an entity: menu items, product media, shipping prices, a collection's products, a shipping zone's warehouses and channels. No stage deletes a top-level entity; `diff` reports them as deletions only. Bulk mutations and chunking for large sections are described in [ADR 001](adr/001-bulk-mutations-optimization.md); thresholds and request pacing are in [LIMITS.md](LIMITS.md).

## Recipes

Recipes are YAML files in `src/recipes`, listed in `manifest.json` (generated by `scripts/generate-recipe-manifest.ts`) and copied to `dist/recipes` at build time. `recipe apply` does not use the deployment stages: it calls `SaleorConfigurator.push`, which applies each section of the recipe in a fixed order and stops at the first failure.
